[`agent.readHistoryCheckpointBasis`](../../docs/control-protocol.md#private-history-persistence-basis).
It checks weak COW project/history identities, revision, path, workspace and
editor context before publishing the existing immutable companion through the
Session worker. It creates no read ticket or file witness. Offline footage can
be preserved in a checkpoint without becoming qualified for inspection, restore
or editing. Stale native state, expired/reused tokens and Stop before publication
refuse without replacing the original file or changing native Undo/Redo.

### Explicit source admission

Native snapshots advertise `sourceAdmission` on native hosts. Exact
`agent.admitSource` binds an already imported, unbound original to its original-owner
asset. `sourceAdmissionBatch` additionally permits a homogeneous exact group of
1–2000 such operations for one workspace in one `agent.apply` publication. Ordinary
editing batches retain their 32-operation bound. Every member needs a distinct native
item, original-owner asset and receipt, plus its explicit path and complete byte
generation. Mixed commands, duplicate identities/receipts, foreign scopes and total
paths over two MiB refuse before staging. No import, relink, interpretation, proxy
selection, inference or external-store mutation is part of this native publication.

The private stage retains only one intermediate binding snapshot and shares one
checking deadline. All member proofs are revalidated before one live history step.
Undo restores the prior complete project/history; guarded Redo separately qualifies
every reintroduced original. This native port alone does not complete human Send:
paired host preparation, progress, durable group ownership and crash/Stop recovery
must use its exact group receipt before full folder intake is qualified.

Ordinary original-file witnesses exclude unbound imports. Admission therefore captures
the complete file hash separately, probes fresh native stream metadata against the
imported metadata, rechecks bytes after probing and again at final publication. These
checks share the operation's cancellation/deadline and execute through the existing
Session worker. The shared native binding implementation and proof metadata publish
as one history step; failed staging preserves human history and Redo. Publication
invalidates the old item decoder cache. Known receipts are historical and never replay
the binding. Guarded Redo separately verifies the actual history target's complete
generation and fresh native metadata before restoring an undone admission, then
invalidates that item's decoder again. Its unbound current state alone cannot qualify
the reintroduced file. The Poema host must obtain challenged owner delivery before this port;
the native complete-byte check does not certify original semantic perception.

Generated native/owner transport acceptance covers MXF ingest, replacement refusal,
lost committed reply, receipt recovery, unchanged cut, native Undo/Redo and saved
reopen. Broader camera/audio layouts, composer admission, knowledge refresh and
source-only perception remain integration work.

### Bound original witnesses

Native snapshots advertise `sourceFileGuard`. An unscoped read retains private
file witnesses for every explicitly bound original File source, including
neighbors outside the active cut. Explicit dependency scopes are described
below. The project, persistence schema and public snapshot do not contain the
private witnesses; public coverage labels cannot recreate one. Identical reads
share their storage.
New/changed File witnesses invalidate only their opened media-pool entries so
a fresh read cannot inherit an old same-path decoder. Old jobs retain their
source Arcs but cannot deliver after their original witness changes.
Witnesses follow the media pool's authorized document-path resolution, including
relative originals beside a saved project; refused foreign paths are never
probed and grant no current file authority.
Limits are 2,048 original File entries and 2 MiB of path data, with complete
refusal rather than truncation. Generated/non-File media needs no disk witness.

The witness includes canonical path, length, modification/creation timestamps
and Unix device/inode plus nanosecond modification/change identity. Precise
sub-millisecond Unix change identity is the fast path, matching original
Poema's media-generation policy. Coarse/non-Unix observations read complete
SHA-256 bytes with fixed 256 KiB memory, checked accounting, before/after file
checks and a 45-second whole-sweep budget. No prefix/sample hash qualifies a
file. This is filesystem continuity, not an immutable-media or adversarial
filesystem guarantee. Byte-identical relocation/touch still requires a fresh
native plan; original Poema may then requalify its historical recorded bytes.

Read validation, ordinary staged publication, owned Undo/Redo and retained
condense candidates recheck these inputs. Candidate media witnesses stay tied
to the original prepare basis: taking a fresh commit ticket cannot renew a
candidate inspected against old footage. Program jobs retain the same witness
and refuse results when originals change. Known committed receipts remain
historical/idempotent after changes and never repeat a write. Historical
checkpoint tickets do not recover fresh media authority; new writes use a new
current read. Ordinary human history operations are unchanged.

Missing/unavailable/nonregular originals remain explicit private states: an
unchanged offline source can be structurally edited without inventing visual
evidence, while removal/reappearance/redirected leaves invalidate an earlier
read. This guard does not prove that legacy descriptions/transcripts/vectors
belong to current bytes, qualify LUT/other finishing resources, independently
certify decoded PTS or validate semantic editing success. Those remain the
original evidence/dependency and output contracts.

The weak-clock fallback runs on bounded workers for background snapshots,
described below. Final write/read validation remains synchronous and may delay
a control request while hashing. The independent operation cancellation door
below can stop guarded publication; it does not make native UI frames run
during hashing or forcibly interrupt a blocked OS call. Large coarse/network
drive latency and complete cancellation coverage still need acceptance. WASM
advertises no native file guard. No live editor or user film is upgraded by
these source changes.

## Background snapshot verification

### Explicit source dependencies

Native `scopedSourceVerification:true` supports an optional `mediaScope` on
`agent.snapshot`, for either synchronous or background reads:

```json
{"token":"fresh-random-token-of-at-least-32-characters","background":true,
 "mediaScope":{"sequences":[5],"sources":[],
               "assets":[{"projectId":"p_film","assetId":"a_camera"}]}}
```

Omit the object for the existing complete bound-original library policy. An
explicit empty object selects the active sequence's dependencies. Additional
sequence IDs, direct media IDs and unique original project/asset bindings expand
that selection; they never replace the active sequence. The currently open
bound original is included too. Unbound monitor metadata remains unverified
discovery so it can be admitted separately. Sequences, subclips and every track
reference, including disabled/muted clips, are traversed with cycle and inventory
bounds. Missing, proxy or unbound file dependencies refuse explicit scoped
qualification. Generated sources need no file bytes. Invalid/null explicit
scopes never fall back to library verification.
Saved condense records share their bounded native parser with this traversal:
member originals and immutable physical-member bases remain dependencies even
when their current pieces no longer display that source. This grants no saved
record freshness or restoration authority; their bytes still need qualification.

The snapshot includes `mediaScope:{kind,items,libraryVerified}`. `kind` is
`dependencies` with sorted covered original-file IDs, or `library` with null
items. `libraryVerified` can only be true for a library read whose bound original
file rows all have current witnesses; it does not qualify unbound imports.
Each source has `fileVerification:verified|unverified|unavailable|generated`.
Unselected sources stay visible as discovery metadata with `unverified`; they
cannot borrow file freshness from a verified neighbor. Missing/refused selected
files are `unavailable`, never current proof. File stamps/hashes stay private.

Postflight, preparation and inspection jobs retain/rebuild the same dependency
set. Combining candidate/read evidence verifies the union and compares every
older witness without renewing changed originals. Native publication checks
both sides of changed sequences, opened sources and restored history against
the ticket. Inserting an unverified source, changing an unverified inactive
sequence, or restoring a source outside the ticket refuses atomically and
requires an explicitly expanded fresh read. Original admission has its separate
complete-byte proof. Program source resolution also refuses an unverified file,
including a dynamically requested source absent from the planned dependencies.

This is a native/private client contract, not a new model-controlled scope or
an automatic switch of the ordinary composer default. The host must adapt source
discovery, knowledge completeness and affected-history scope before enabling
scoped reads there. Full hashing, final publication validation, cancellation and
the existing deadlines remain in force. Two large selected originals can still
be expensive; scoped success does not certify interactive latency.

`sourceCatalogProjection:true` supplies `agent.readSourceCatalog` with an explicit
workspace `scope:{projectId,anchorSequence}`. It reads only current project data,
returning `status:metadata`, `kind:native_source_catalog`, `version:1`,
`nativeSession`, `revision`, `project:{path,dirty}`, `sequence` and complete
`sources:[{item,name,binding,file}]`. `requiresSourceValidation:true` and
`writeAuthority:false` are mandatory. There is no token, original-file path,
stat, decode, file witness or history write. The catalog refuses malformed or
oversized metadata (100,000 project items, 1,024-byte source names, bounded
bindings and seven MiB of serialized rows) rather than silently truncating.
Compare its metadata basis/roster with the subsequent fresh guarded snapshot;
this is dependency selection, never an edit or renewed source generation.

Snapshots also advertise `guardedOperationDeadlineMs:45000`, derived from the
same constant enforced by native verification. A host with independent
`operationCancellation` and `sourceFileGuard` may wait up to 47 seconds for the
four guarded publishers while retaining short ordinary control deadlines. The
native 45-second budget, publication fence and uncertain-reply semantics are
unchanged. Progress/status is display evidence; it does not prove rollback or
permit replay of an edit whose response was lost.

`historyCheckpointOperations:true` extends that worker and independent Stop
fence to private history checkpoint save/restore. They keep full original-byte
validation and the 45-second native budget; compatible hosts may wait 47 seconds
for their response. The real Session remains exclusively on the worker while
the UI holds an inert display projection. Stop before publication prevents the
checkpoint file or restoration; late/uncertain outcomes never permit replay.

Native `agent.snapshot {token,background:true}` starts an original-file witness
worker and returns a `native_snapshot_verification` job envelope, never an edit
ticket. The worker receives only immutable authorized paths and cancellation
state, not a Session, project writer, media cache or ticket authority. Path
resolution uses the same document-origin resolver as the media pool.

`agent.snapshotStatus {job:token}` polls the same job. Delivery checks current
project identity/revision, path, sequence, editor context and path authorization
on the engine thread before issuing a snapshot ticket. The result advertises
`backgroundSnapshots:true`. Subsequent polling does not reissue the ticket.
Progress counts completed observations against two sweeps and transports the
byte count as a decimal string, not a potentially rounded JavaScript number.

`agent.cancelSnapshot {job:token}` stops future qualification and revokes any
unused delivered ticket with that token. It never erases a committed receipt,
replays work or undoes an edit. Unknown cancellation retains a bounded tombstone
so a delayed start cannot revive the canceled read. Worker cancellation and the
45-second deadline are checked between full-byte chunks and observations; a
blocked operating-system call may finish later, but cannot issue late authority.

There are at most two actual verification workers globally and four retained
jobs per session. Canceled workers retain their permit until the thread exits,
so repeated Stop cannot create unbounded blocked threads. Workers catch panics,
report errors and never publish to the cut. An active job is not evicted to
admit another. The synchronous snapshot form remains available for compatible
readers; it cannot reuse an active background token. WASM has no native worker.

Nine deterministic native job tests cover responsiveness during a blocked read,
Stop before/after completion and ticket delivery, document/context/authorization
changes, failed/deadline workers, permit bounds, hostile arguments, preserved
committed receipts and the existing final publication guard. A byte-reader test
refuses cancellation after one chunk instead of returning a partial digest.
Actual TCP/Poema acceptance covers explicit cancellation and Stop at delivery.

This is an initial-read lifecycle, not a replacement for the final native
publication guard. The synchronous `validateSnapshot` form, ordinary edit
publication, candidates, history and legacy Program inspection polling still
call synchronous witness validation.
Client disconnect or timeout after a sent write is unknown unless the separate
operation cancellation door proves pre-publication cancellation. Late, missing
or malformed acknowledgements require receipt reconciliation, not rollback.
Actual slow/network-drive acceptance and complete cancellation coverage remain
required; no prefix hashes or weaker metadata shortcut replaces complete
weak-clock verification.

## Background post-perception validation

Native snapshots advertise `backgroundValidation:true`. A caller may start
`agent.validateSnapshot {token,job,candidate?,inspection?}` using its existing
read ticket and one fresh verification-job ID. This creates no read ticket,
history step, cache invalidation or publication authority. The worker captures
complete original-file witnesses through the same media guard and compares
them with the original read, optional candidate and completed inspection inputs.

`agent.validationStatus {job}` delivers one current result only after the live
project identity, revision, path, sequence, authorized path plan, candidate basis
and exact completed inspection ownership still match. The completed worker
result expires after 250 ms if it is not delivered; an absent caller cannot
retain an old proof indefinitely. An inspection must belong to the same read
ticket and candidate/live view. No live-view substitution is allowed.

`ticketRevoked:false`. The original read ticket retains its ordinary scope and
final publication checks; the verification-job ID cannot authorize an edit.
Canceled IDs retain bounded tombstones to reject delayed starts. Neither expired
nor interrupted verification is restarted automatically. Workers share the
two-thread global pool with snapshot jobs, retain permits until actual exit,
and have four retained validation jobs per session and a 45-second read budget.
Progress exposes bounded observation counts and decimal-string bytes.

Poema's Program preflight and postflight use these workers when both native
background validation and original-file guards are advertised. Postflight names
the exact retained completed inspection, replacing redundant fresh snapshots
and an additional synchronous inspection poll. Older engines retain the prior
checks. Final native write/history guards and ordinary inspection/candidate
validation remain intact, so this change alone does not qualify complete UI
responsiveness or slow-drive library scale.

Native tests cover worker availability and bounds, changed originals, COW/path/
ticket changes, Stop/tombstones, expired delivery, exact inspection ownership,
hostile arguments and worker panics. Actual TCP/Poema tests exercise postflight,
Stop at delivery, no minted edit authority, source replacement and intervening
human edits with preserved native Undo.

## Guarded operation cancellation

The desktop transport handles `engine.cancelOperation {token}` on its connection
thread, not through the UI request queue. It holds only a session-local
`AgentOperationControl`, never a Session, project writer or history handle.
Native snapshots advertise `operationCancellation:true` only after the host
installs this independent door. WASM and serial/headless hosts without it do
not advertise the feature. No generic model executor or model Cancel tool is
introduced.

The token is an already-issued native read ticket, not a path or a recipe.
Only `agent.apply`, `agent.undo`, `agent.redo` and `agent.commitCondense` use
this publication fence. This includes ordinary/parameter/Source-mark/sequence
creation edits and native candidate/restoration/version publication through
their existing audited handlers. It does not cancel arbitrary human commands,
source curation, export, file/history-checkpoint writes, read-side validation
or candidate preparation.

Their existing full media guards receive one shared cancellable 45-second
checking budget starting at operation execution. Stop is checked between
complete-byte chunks and observations, then at an atomic fence immediately
before the SAME native commit/Undo/Redo operation. No worker publishes an edit,
no final file check is removed, and no metadata-only shortcut replaces hashing.
An already-blocked OS call can finish later, but an accepted cancellation
cannot subsequently cross the publication fence with that ticket.

Replies contain only `token`, `status` and `cancellationAccepted`. `cancelled`
with true permanently revokes that ticket for guarded publication. Once the
fence wins, cancellation returns `publication_started` or historical `committed`
with false. Unknown/expired and rejected tickets return false and do not
manufacture cancellation authority. Historical commit receipts remain readable
and idempotent, including after human Undo; cancellation never reverses them.
A known pre-publication validation refusal preserves the prior retry contract
unless cancellation won; interrupted/panicked operations are not reopened.

The cache holds at most 256 issued scopes and never evicts the active operation.
Panic unwinding releases the active scope without reviving its ticket. Tests
cover cancellation before execution, during staged publication and the complete
byte guard, cancelled Undo/Redo/candidate commit, late and historical replies,
token bounds, panic cleanup and Cancel/publication races. The actual desktop
transport test proves that Cancel bypasses a queued UI request. A separate
generated TCP/Poema case proves Stop, delayed-request refusal, a fresh valid
write and non-replaying late receipt reconciliation. These do not certify
continuous GUI responsiveness or actual slow/network-drive performance.

Poema forwards Stop to every supported native publisher. On a sent-write error
it requests bounded cancellation over a separate connection. Only a strictly
validated accepted reply establishes nonpublication. Older engines and late,
lost or malformed cancellation retain unknown-write semantics and never trigger
an automatic edit retry. Native UI hashing remains synchronous; moving slow
verification off that thread without weakening these fences remains work.

## Private durable native history checkpoints

`historyCheckpoint` advertises native-only trusted recovery commands, not model

`agent.saveHistoryCheckpoint {token,scope,workspace,checkpoint}` writes an

unused ticket, matching film/workspace and bound originals. Saving changes no
project, view, revision, history or journal. The companion is private (0600 on

The companion preserves the complete bounded native Undo/Redo snapshot graph,

adopt a replacement document or human history. Sixteen recent save guards are

Expired guards and changed human history refuse.

Restore imports the graph, advances the revision to invalidate prior reads,
preserves clean/dirty classification and returns an idempotent historical
`history_restore` receipt. It adds no ordinary Undo step. Live recovery retains
current merge ownership; a new process does not resume an old UI gesture.
Subsequent guarded Undo/Redo uses the SAME native snapshot/history operations.
Private files and a caller-supplied digest are integrity/provenance machinery,
not cryptographic user authorization or a general file-import API.

Ten native regressions cover reopen, both branches, consumed Undo, prior human
work, identical-value distinct snapshots, exact native integers/auto points,
expired read tickets, replacement identities, merge ownership, hostile input,
private/symlink/truncated/oversized companions and atomic rejection. A generated
TCP acceptance actually terminates one native process, reopens its saved
project in another, restores history and verifies guarded Undo/Redo plus the
earlier human step. The fixture can save/reopen only in an explicitly marked
parent-owned generated directory, never an ordinary workspace.

Poema has strict private typed save/restore transport with no retry after lost
or malformed replies. Managed saved workspace/coordinator recovery is connected
